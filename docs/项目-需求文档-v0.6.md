# HR 端招聘 Agent 项目需求文档 v0.6

> 状态：现行需求；2号通用话术选择已完成离线实现，真机待验
> 更新：2026-10-27
> 当前范围：1号主动招呼、2号首次新招呼回复

## 1. 项目目标

系统以确定性状态机控制 BOSS 直聘 Android 客户端，在页面识别、身份校验、幂等和发送回读约束下完成两类招聘沟通：

- **1号状态机**：读取牛人简历，形成岗位评估，通过时发送一次首次招呼。
- **2号状态机**：处理“新招呼”中的候选人消息，由 Agent 从已核验常用语中选择与当前语境匹配的回复。

Agent只形成结构化判断和选择话术；设备动作、发送授权、幂等、重试与终态由确定性代码控制。3号多轮跟进尚未实现。

## 2. 全局安全边界

- 不以性别、年龄、照片、婚育、民族、健康状况等敏感属性作招聘决策。
- 不生成、改写、拼接或输入自由聊天文本，只允许使用 `config/reply_phrases.yaml` 中已核验的内置话术。
- 不自动安排面试、发送 Offer、拉黑、举报或删除会话。
- 页面、身份、消息、话术或发送结果不确定时停止或转人工。
- 不破解验证码、规避平台风控、实施多账号群控或反检测对抗。
- 真机自动化测试暂停；恢复前须由需求方明确授权并设定运行时长、动作量和人工停止条件。

## 3. 1号状态机

1号从牛人列表按页面顺序向下遍历，复用公共采集器逐屏展开折叠正文并采集简历，对照岗位画像形成评语和 `greet/do_not_greet/needs_review` 决策。

- `greet`：现场身份、终态和“立即沟通”按钮均通过硬闸后发送。
- `do_not_greet`：不发送，返回列表。
- `needs_review`：不发送，交人工处理。

评语去除首尾空白后必须非空；100–300字仅为质量建议，超出范围仍保存原文。只有回读到送达信号才记 `sent`，不能确认时记 `unknown`；已封口终态不得自动重复触达。

## 4. 2号状态机

2号以“新招呼”列表作为业务入口，确认当前候选人入站消息并读取简历后，由Agent分析可见语境并从允许清单中选择回复：

- 没有实质聊天背景或其它问题时，优先询问工作地点是否可以接受。
- 候选人提出其它问题时，优先选择能直接回应问题的已核验常用语，不强制先问地址。
- 候选人明显不符合岗位时，可以选择已核验的婉拒话术。
- 没有安全匹配的话术、语义不确定或信息不足时，挂起人工处理。

“自由选择”只表示Agent可以在允许清单内按语境选择，不表示可以生成或输入自由文本。同一入站消息只能建立一个回复动作，发送前必须重新核验会话、消息和话术，发送后必须回读出站气泡。

当前代码已经采用 `send/hold + phrase_key + reason` 契约并开放完整允许清单；地址确认只作为无其它问题时的策略优先项，不是代码强制分支。真机验证因2026-10-27事故暂停。

## 5. 公共能力与数据边界

两套状态机共享设备控制、页面守卫、简历采集、评语规则、日志与证据能力；回复链路另共享 `ReplyPlan`、消息方向、话术定位、发送边界和回读能力。公共层不决定业务发送，1号与2号不共享动作终态或恢复策略。

1号使用 `data/hr_agent_v2.sqlite3`，2号使用 `data/reply_agent.sqlite3`。当前结构以两份数据库建表文档和 `data/*.sql` 为准；候选人、简历快照与业务动作分离的目标及理由见ADR-0003。数据库只保存业务事实、幂等、发送边界和终态，不保存逐步调试流水。

## 6. 当前阶段

- 1号和2号的现有实现已通过离线测试；2号通用话术选择无需改动现有表结构，精确意图由 `phrase_key` 表达，旧 `decision` 字段保留为兼容分类。
- 2026-10-27单账号长时间连续运行后被人工确认封号；程序只观测到设备掉线，不能据此推导安全运行阈值。工程结论见 `docs/项目-实测记录-v0.1.md`。
- 在无法进行真机验证期间，只开展文档、离线测试、数据模型和纯代码重构；不得把离线通过写成实机可用结论。

## 7. 完成标准

- 默认dry-run不产生外部消息。
- 任何不可逆动作都有发送前硬闸和发送后回读。
- 相同候选人首次招呼或相同入站消息不会被重复发送。
- 2号只能选择已核验常用语；无法安全匹配时转人工。
- 页面未知、身份不一致、风控信号和结果不明均保守停止或封口。
- 需求、实现、数据库结构和测试之间的偏差必须显式记录，不能以文档改写代替实现。
