# ADR-0003：候选人事实与简历快照分离

- **状态**：已接受，待形成目标建表文档和迁移实现
- **日期**：2026-10-24
- **最后同步**：2026-10-27
- **范围**：1号、2号共用的数据模型原则

## 背景

当前 `candidate` 同时承载身份、可选简历区块、评估、1号动作和证据。平台新增简历区块会推动加列，2号也被迫携带1号动作字段；这些数据的生命周期并不相同。

## 决策

- 稳定身份放入 `candidate`。
- 每次简历采集形成 `resume_snapshot`，基本资料和求职期望放入 `core_json`，不定形的工作、项目、教育、作品等区块放入 `sections_json`。
- 评估独立于简历快照；1号首次招呼动作与2号回复动作分别维护。
- 高频且稳定的查询字段才能提升为物理列或索引；不为每种可选简历区块建列或子表。
- 业务表只保留幂等、发送边界、终态和必要审计时间；逐步XML、PNG、坐标和调试流水留在运行目录。

## 文档归属

本ADR只记录为什么拆分和采用关系字段加JSON的混合模型，不充当目标DDL。正式实施前，应由新版数据库建表文档完整定义表、列、类型、约束、索引和版本；`data/*.sql` 是其SQLite可执行实现，实际 `.sqlite3` 是运行时物理事实。

## 迁移约束

- 正式库先建立只读备份，迁移只在副本执行。
- 保留现有动作主键、唯一约束、发送边界和终态；建立必要的新旧ID映射。
- 迁移前后核对行数、终态分布、唯一键和外键，并通过离线测试。
- 未完成目标建表文档、迁移脚本和回滚说明前，不覆盖现用数据库。

## 取舍

继续加列会持续制造DDL噪声；每种区块一张表会增加不必要的查询和迁移成本；全部塞入单个JSON又会丢失稳定身份和业务约束。混合模型在可扩展性和可审计性之间更平衡，但仍受平台稳定ID不可得的限制。
